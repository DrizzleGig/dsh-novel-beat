# DSH Novel Beat｜拍板

> AI 可以替你写故事，但不能替你决定故事怎么走。

![npm version](https://img.shields.io/npm/v/dsh-novel-beat)
![license](https://img.shields.io/badge/license-MIT-blue)
![stars](https://img.shields.io/github/stars/DrizzleGig/dsh-novel-beat)

一个面向 AI 小说写作的剧情决策插件：AI 写作过程中，遇到会改变故事走向的节点时暂停下来，把不同走向和代价交给作者选择；拍板后继续写作，写完再核对关键剧情有没有落实。

- 找出会改变故事走向的关键剧情节点
- 为每个节点提供 2–4 个不同走向及其代价
- 由作者决定，记录已经确认的剧情事实和未完成的承诺
- 下一章开始前，重新呈现需要延续的剧情记录
- 正文完成后，核对关键变化和前后矛盾

**默认关闭** · **独立插件** · **不写正文**

## 前言

这个插件是从一个很实际的问题开始做的：我希望 AI 帮我写小说，但不希望它写着写着，就替我决定了整本书的走向。

尤其是长篇小说，人物知道什么、答应过什么、东西现在在谁手里，这些事情看起来不起眼，写多了却很容易乱。

我不想再靠不断追加提示词，提醒 AI 不要忘记之前的剧情。所以我做了「拍板」，把重要剧情决定单独拿出来，让作者确认，并且留下记录。

它不是另一个正文生成器，也不是自动审稿工具。它只处理一件事：重要剧情由作者决定，已经决定的事情在后续写作中有据可查。

## 快速开始

不需要改变原来的小说写作方式，也不需要一直开启插件。

### 1. 安装

```bash
dsh plugin --profile web add dsh-novel-beat
```

或者直接从 GitHub 安装：

```bash
dsh plugin --profile web add github:DrizzleGig/dsh-novel-beat
```

装好后重启 Harness。插件可以独立使用，不需要安装其他写作插件。

### 2. 开启

默认关闭。在需要处理重要剧情的章节开始前，输入：

```text
/beat on
```

也可以点击输入框旁边的「拍板」按钮开启。

### 3. 开始写作，在关键处拍板

像平常一样告诉 AI 写第几章、继续写，或者接下来怎么发展。

AI 会正常推进正文。遇到可能改变故事走向的关键节点时，「拍板」会暂停写作，提供 2–4 个不同走向及其代价。

选择你认可的方向，AI 就会接着写。章节完成后，再进行结构核对。

第一次使用时，可以直接拿一个涉及秘密、人物关系或重要物品的章节试试。

## 一个熟悉的写作场景

你让 AI 继续写一段秘境夺宝的剧情。

主角跟随宗门队伍进入一处上古药园，意外发现一株即将成熟的「凝元草」——此药能稳固筑基根基，对灵根资质普通、筑基多年无望的修士而言，称得上难得的机缘。

AI 写到这里，忽然停了下来。

药草周围看似没人迹，泥土下却残留着几道极淡的禁制纹路，旁边还有一截被剑气削断的阵旗。有人先来过，而且布下的禁制并未完全消失。更麻烦的是，药草成熟时灵气外溢，附近修士迟早会察觉。主角若取走灵药，或许能换来一次筑基的机会；若被人发现，不仅可能暴露自己的修法和手段，还可能卷入前人留下的因果。宗门虽有先到先得的规矩，却也禁止弟子私毁同门或他派修士的禁制。

此时，主角该如何取舍？

**A｜先探禁制，再谋灵药**：不急着采摘，借纸人和阵盘探明禁制残留，确认没有埋伏再动手。耗费符箓与时间，但能尽量摸清风险，代价是可能错过灵药成熟的时机。

**B｜布下后手，伺机取药**：暗中布置隔绝阵法与退路，待灵药成熟便迅速采走。收益最大，也最符合谨慎行事的习惯；但若禁制另有主人，取药可能结下因果，甚至引来筑基修士追踪。

**C｜暂避锋芒，记下位置**：以当前修为不值得为一株灵药冒险，先留下隐蔽标记，退出药园，等其余修士探路后再判断。保住性命与底牌，却可能眼看机缘落入他人之手，也可能因灵药被采而失去筑基机会。

**D｜借他人之手，坐观其变**：暗中引导其他修士接近药园，观察禁制反应与守药之人的手段。能借势降低自身风险，但稍有不慎便会暴露行踪，甚至被卷入宗门规矩与他派恩怨。

作者选择 C，或修改其中的条件与代价。AI 便从这个节点继续写：主角如何留下标记、如何隐匿气息、后来又如何面对灵药被他人捷足先登的可能；章节结束后，再核对他是否真的保住了底牌、是否留下了退路，以及这次取舍是否影响后续筑基之路。

决定由作者下，AI 负责把代价写出来。

## 为什么使用拍板

| 常见做法 | 卡在哪里 | 拍板怎么做 |
|---|---|---|
| 直接让 AI 自由发挥 | AI 可能擅自揭露秘密、增加人物关系 | 在剧情推进到关键节点时暂停写作，提供不同走向，由作者确认后继续 |
| 在提示词里反复强调人物设定 | 长篇写作容易遗漏细节 | 记录已经确认的剧情事实 |
| 靠自己记住所有伏笔 | 承诺、交易和未完成事件容易遗忘 | 持续记录尚未完成的剧情义务 |
| 每章写完人工通读 | 很难逐项核对所有关键变化 | 按照已确认的记录进行结构核对 |
| 每次开新章节重新解释前情 | 信息重复，仍然可能遗漏 | 下一章开始前提供全书剧情记录 |

它不是让 AI 少写，而是让 AI 在重要剧情上少替作者做主。

## 你会怎么使用它

「拍板」落在两个时刻：写作中停下来问你，写完后替你核对。

### 作者会说的话 → 拍板会做什么

| 作者会说的话 | 拍板会做什么 |
|---|---|
| 这章主角要拿到一件重要物品，但后续怎么发展还没决定。 | 找出可能改变故事走向的节点，提供不同选择。 |
| 这个秘密暂时不能让所有人知道。 | 将秘密的知情状态作为需要确认的剧情变化。 |
| 这两个人到底要不要合作？ | 提供不同的人物关系走向及其后续影响。 |
| 上一章答应的事情，这章要兑现吗？ | 提醒尚未完成的承诺和义务。 |
| 这章写完了，帮我看看有没有漏掉之前决定的事情。 | 核对已决定的剧情变化有没有落实。 |
| 下一章开始之前，先看看还有哪些事情没解决。 | 呈现已经确立的事实和未完成的剧情义务。 |

### 没有拍板 / 有拍板

| 没有拍板 | 有拍板 |
|---|---|
| AI 自己决定谁发现了秘密 | 先让作者决定秘密由谁发现 |
| AI 自己安排人物立场变化 | 先比较不同立场变化的后果 |
| AI 可能忘记之前的承诺 | 把尚未兑现的承诺留在全书记录中 |
| AI 可能擅自转移关键物品 | 核对物品归属有没有被错误改变 |
| 写完只能自己逐段检查 | 写完核对关键剧情变化 |
| 下一章重新解释前面的剧情 | 下一章可以沿用这本书的剧情记录 |

## 核心功能

### 1. 关键剧情决策

识别章节中可能改变故事走向的事件。

例如：

- 谁知道了一个秘密？
- 谁站到了哪一边？
- 谁欠了谁？
- 一件重要物品到了谁手里？
- 哪个承诺即将到期？
- 哪段人物关系发生了变化？

每个需要处理的节点提供 2–4 个不同走向，以及相应代价和后续影响。

不是简单地把同一个选择换几种说法，而是让作者看到不同决定会把故事带向哪里。

### 2. 全书剧情账本

作者确认的决定会进入本书共用的账本。

主要记录两类信息：

**已经确立的事实（Canon）**

例如：

- 凝元草仍在药园里，主角只留了标记，没有采走。
- 泥土下的禁制还在，那截阵旗不是宗门之物。
- 主角没有暴露纸人和阵盘。

**尚未完成的义务（Obligations）**

例如：

- 灵药成熟前，主角必须决定取不取、怎么取。
- 禁制的主人迟早会查到来过药园的人。
- 药园灵气外溢，附近修士会陆续赶来，宗门也会清点。

这些信息会在后续章节中继续发挥作用。

### 3. 下一章剧情提醒

开始下一章之前，可以重新呈现这本书已经确立的事实，以及仍然需要处理的承诺和义务。

避免人物突然知道不该知道的事情，也避免前面约定过的内容在后续章节中无故消失。

### 4. 写后结构核对

正文完成后，检查：

- 已经决定发生的关键变化有没有发生。
- 人物秘密知情状态有没有出现不符合记录的变化。
- 人物关系和物品归属有没有出现结构性矛盾。
- 已经记录的承诺和义务有没有被错误忽略或提前结清。
- 有没有出现与已有剧情事实冲突的内容。

发现问题后指出不一致，由作者决定是否修改。

## 适合谁

**适合：**

- 日更网文作者：章节更新频繁，需要维护剧情连续性。
- 长篇连载作者：人物多、关系复杂、伏笔和承诺多。
- AI 辅助写作的作者：希望提高效率，但不希望 AI 擅自决定关键剧情。
- 有明确剧情规划的作者：希望自己掌握故事方向，而不是每次都被 AI 的发挥带着走。

**不太适合：**

- 只需要 AI 直接生成正文的用户。
- 只写简单日常场景、不涉及重要剧情变化的用户。
- 希望插件自动判断文笔、情绪、节奏和人物塑造质量的用户。

短篇也可以使用，但如果故事没有复杂的关系、秘密和长期因果，启用它的必要性可能不高。

## 它不做什么

这里有几条必须说清楚的边界。

- **不写正文。** 不接管原本的正文生成模型和写作流程。
- **不替作者决定。** 它提供不同走向，最终选择权在作者手中。
- **不擅自修改 Canon。** 模型猜测不能直接成为已经确立的剧情事实。
- **不评价文笔。** 写后校验只做结构核对，不判断句子是否优美、人物是否鲜活、情绪是否到位。
- **不保证发现所有错误。** 校验依赖已经记录的剧情事实和结构化信息，不能代替作者通读正文。
- **不强制全程开启。** 默认关闭，作者在需要时主动启用。
- **不依赖其他插件。** 可以独立安装和使用。

它不是一个自动替你管理整本小说的作者代理。

它只是把那些容易被 AI 擅自决定、又容易在长篇写作中遗忘的事情，交还给作者掌控。

## 常见问题

### Q1：拍板会不会修改我的正文？

不会。

「拍板」不负责生成或改写正文。它负责写作过程中的剧情决策和写后结构核对。

发现不一致时，它会指出问题，具体怎么修改由你决定。

### Q2：使用它需要联网吗？

插件本身不联网，也不上传你的正文或账本。它只读写你工作区里的账本文件。

需要联网的是模型服务本身——那是 DeepSeek Harness 和你接入的模型的事，与这个插件无关。

### Q3：剧情账本存在哪里？

剧情记录保存在本书对应的 `book.json` 中，位于工作区的 `.dsh-novel-beat/<书名>/` 目录下。

它是全书共用的数据，不是每章重新创建的一份临时笔记。需要备份或迁移小说时，应当同时保留对应的账本文件。

### Q4：如果剧情没有拍完，能不能硬写？

`beat_gate` 会检查必要的剧情决策是否完成。

未完成时可以返回：

```text
pass: false
```

表示当前决策检查没有通过。

它提供的是流程门控信号；实际能否绕过门控继续写作，取决于 Harness 中的调用和执行流程。不能把它理解为不可绕过的系统级锁。

### Q5：短篇小说也用得上吗？

可以。

例如短篇中涉及身份揭露、人物背叛、秘密曝光或关键承诺时，也可能需要作者提前决定。

不过，短篇通常不需要维护大量跨章节的剧情记录。如果故事简单，直接写作会更方便。

### Q6：会不会和其他写作插件冲突？

「拍板」不依赖其他 DSH Novel 插件，可以独立运行。

它主要使用 `beat_*` 工具和自己的 `book.json` 账本，不要求其他插件接管正文或共享内部状态。

如果同时使用其他写作插件，仍需要留意 Harness 的工具注册、命名冲突和各插件对同一剧情事实的处理方式。

插件之间能否无冲突协作，不能仅凭独立安装就作出保证。

## 技术信息

以下内容主要面向开发者和希望了解内部工作流程的用户。

### 项目基本信息

| 项目 | 内容 |
|---|---|
| 插件名称 | dsh-novel-beat |
| 中文名称 | 拍板 |
| 运行环境 | DeepSeek Harness |
| 工具数量 | 7 个 beat_* 工具 |
| 默认状态 | 关闭 |
| 独立运行 | 是 |
| 正文生成 | 不负责 |

### 工具入口

| 工具 | 作用 |
|---|---|
| `beat_plan` | 登记本章的决策点；每个节点 2–4 个真分叉，每个选项都带「会改变什么」 |
| `beat_list` | 看全书或本章的决策与账本；`context:true` 时返回 canon、未回收义务和最近决策 |
| `beat_decide` | 记录作者的选择；改主意用 `supersede` 并写原因 |
| `beat_gate` | 写正文前体检；还有没拍板的就返回 `pass:false` |
| `beat_compile` | 产出本章约束：必须发生、证据、不得出现、既有义务、全书 canon |
| `beat_verify` | 写后校验：缺变化、踩禁项、到期义务没回应，都会报出来 |
| `beat_adjust` | 作者主权动作：豁免义务、推翻旧决策，必须写原因 |

### 数据在哪

```text
<工作区>/.dsh-novel-beat/<书名>/book.json
```

单文件账本，包含 decisions / canon / obligations / chapters / audit。

### 设计原则

- 作者确认优先于模型推测。
- 已确认的剧情事实不能被随意改变。
- 未完成的剧情义务需要持续保留。
- 写作过程中的实时决策与写后结构核对分开处理。
- 结构核对不越权评价文学质量。
