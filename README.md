## 关键剧情，不替你做主。

AI 写小说时，遇到会改变故事走向的关键岔路，不再替你顺手决定。

「拍板」会暂停写作，给你 2–4 个**真正不同**的剧情走向，说明每个选择的代价与后续影响。你来决定，结果写进全书账本，后续章节据此继续。

**你决定故事怎么走，AI 负责把故事写下去。**

```text
发现关键岔路 → 提出不同走向 → 作者拍板 → 写作一段 → 登记入账 → 再问下一个 → 写后结构核对
```

**默认关闭** · **独立插件** · **不写正文**

> 0.7.0 的账本契约（[`docs/adapter-contract.md`](./docs/adapter-contract.md)）与 Conductor 协议（[`docs/conductor-adapter.md`](./docs/conductor-adapter.md)）已冻结，兄弟插件可以按契约读账本、按协议接调度；进程内另有只读服务 `ctx.get('novelBeat')`。

## 快速开始

不用改变原来的写作方式，也不用一直开着。

### 1. 安装

```bash
dsh plugin --profile web add dsh-novel-beat
```

或直接从 GitHub 安装：

```bash
dsh plugin --profile web add github:DrizzleGig/dsh-novel-beat
```

装好后重启 Harness。插件可独立使用，不需要其他写作插件。

### 2. 开启

默认关闭。在要处理重要剧情的章节开始前：

```text
/beat on
```

也可以点输入框旁边的「拍板」按钮。

### 3. 写作，在岔路口拍板

像平常一样告诉 AI 写第几章、往下写。AI 正常推进正文；遇到会改变故事走向的节点时，「拍板」停下来，给出 2–4 个走向和各自的代价。你选定方向，AI 接着写这一段落账，写完再做结构核对。

第一次用，可以拿一章涉及秘密、人物关系或重要物品的剧情试试。

## 一个真实的写作场景

你让 AI 继续写秘境夺宝这一场：主角随宗门队伍进入上古药园，发现一株即将成熟的「凝元草」——能稳固筑基根基，对灵根普通的修士是不可多得的机缘。

AI 写到这里停了下来。药草周围看着没人，泥土下却残留着极淡的禁制纹路，旁边还有一截被剑气削断的阵旗：有人先来过，布下的禁制也没散干净。而灵药成熟时灵气外溢，附近修士迟早察觉。宗门有先到先得的规矩，却也禁止弟子私毁同门或他派修士的禁制。

**A｜先探禁制，再谋灵药**：借纸人和阵盘摸清残留，确认没有埋伏再动手。多耗符箓与时间，可能错过灵药成熟。

**B｜布下后手，伺机取药**：暗中布下隔绝阵法与退路，成熟即采。收益最大；但若禁制另有主人，可能结下因果、引来筑基修士追踪。

**C｜暂避锋芒，记下位置**：留个隐蔽标记先退，等别人探路再判断。保住性命与底牌，也可能眼看机缘落入他人之手。

**D｜借他人之手，坐观其变**：引其他修士接近药园，观察禁制反应与守药人的手段。能借势降风险，一旦失手就暴露行踪、卷入两派恩怨。

你选 C。AI 从「主角如何留下标记、如何隐匿气息」接着写；这一段落账，下一章之前它还记得主角没取药、禁制还在、灵药随时可能被别人拿走。章节写完再核对：他是不是真保住了底牌、留没留退路。

**决定由你下，AI 负责把代价写出来。**

## v0.7.0：从模型自觉到引擎兜底

0.6 是「告诉模型在关键处停下来问作者」——问不问、记不记得记，靠模型自觉。0.7 改成插件引擎兜底：`/beat on` 之后，写作只有一种节奏。

> 一次只问一个岔路 → 你答 → 写这一段 → 登记这一段 → 再问下一个

- **逐段写作**：一次只处理一个剧情岔路。上一段没登记成段落，下一题不会发（`segment-required`）。
- **段落有据可查**：每段保存正文快照、算出区间与 hash，登记成功时把这段正文回显给你看。
- **安全回退**：退第 N 段，它后面所有段一起作废，canon 与义务倒序还原；正文被手改过就先按快照重新定位，定位不到就拒绝、一个字都不动。
- **决定权始终在你**：可以选 AI 给的走向，也可以 `/beat fork` 自己插一条岔路，让它先写成决策点再往下问。

正文字数没登记成段落时，下一个岔路问不出来（`write-ahead`）；整章闷头写完再回头问，走不通。这套闸门是**工具面内的协议**，不是系统级沙箱——AI 若绕开工具直接改文件，插件看不见，只能靠 `beat_verify` 的 `unsegmented` / `drift` 事后发现。

## 怎么用它

「拍板」落在两个时刻：写作中停下来问你，写完后替你核对。

### 你大概会这样说

| 你说的话 | 拍板会做什么 |
|---|---|
| 这章主角要拿到一件重要物品，后续怎么发展还没定。 | 找出会改变走向的节点，给出不同选择。 |
| 这个秘密暂时不能让所有人知道。 | 把「谁知道」当成需要确认的剧情变化。 |
| 这两个人到底要不要合作？ | 给出不同的人物关系走向及其后续影响。 |
| 上一章答应的事，这章要兑现吗？ | 提醒还没完成的承诺和义务。 |
| 这章写完了，帮我看看有没有漏掉之前定的事。 | 核对已决定的剧情变化有没有落实。 |
| 下一章之前，先看看还有哪些事没解决。 | 呈现已确立的事实和未完成的义务。 |

### 四件事

**关键剧情决策**：识别可能改变故事走向的事件——谁知道了秘密、谁站到哪一边、谁欠了谁、重要物品到了谁手里、哪个承诺要到期、哪段关系变了。每个节点给 2–4 个真不同的走向，不是把同一个选择换几种说法。

**全书剧情账本**：你确认的决定进本书共用的账本，主要记两类——已经确立的事实（Canon，如「凝元草仍在药园，主角只留了标记」）和尚未完成的义务（Obligations，如「禁制的主人迟早会查到来过药园的人」）。

**下一章提醒**：开新章前呈现这本书已确立的事实和待处理的义务，避免人物突然知道不该知道的事，也避免约定过的内容无故消失。

**写后核对**：正文完成后检查关键变化有没有发生、秘密知情状态对不对、人物关系与物品归属有没有结构性矛盾、承诺有没有被错误忽略或提前结清。发现问题只指出不一致，改不改由你定。

### 作者侧命令

| 命令 | 作用 |
|---|---|
| `/beat on` / `/beat off` | 开关拍板模式（关闭后工具、技能、闸门全部撤下） |
| `/beat status` | 看模式、受保护目录、当前章还有几个岔路没问 |
| `/beat body [路径\|reset]` | 增删受保护的正文目录（默认 `正文`） |
| `/beat list [章]` | 列本章已登记的段落（段号 / 字数 / 挂了哪些决策） |
| `/beat revert [段号]` | 退这一段重写（不传段号=最后一段，它后面的段一起作废；正文被改过时加 `!` 表示按原文定位照退） |
| `/beat fork <要决定什么>` | 自己插一条岔路，模型必须先把它写成决策点再往下问 |

输入框上方还有一条**拍板台**（只在 `拍板：开` 时出现）：左边显示「第 N 章 · K 段 · 最后一段 X 字」，右边两个按钮——「重写这一段」（等于 `/beat revert`，级联作废）和「刷新」（重新读账本）。刚读完一段觉得不行，直接点按钮，不用记段号。

## 适合谁

**适合**：日更网文作者（更新频繁，要维护连续性）；长篇连载作者（人多、关系复杂、伏笔多）；用 AI 辅助但不想让 AI 擅自决定关键剧情的作者；有明确剧情规划、想自己掌握方向的作者。

**不太适合**：只想要 AI 直接生成正文的用户；只写简单日常、不涉及重要剧情变化的用户；希望插件自动评价文笔、情绪、节奏和人物塑造的用户。短篇也能用，但故事简单时开它的必要性不高。

## 它不做什么

- **不写正文**：不接管正文生成模型和写作流程。
- **不替作者决定**：只提供走向，选择权在你。
- **不擅自改 Canon**：模型猜测不能直接变成已确立的剧情事实。
- **不评价文笔**：写后核对只做结构，不判断句子是否优美、人物是否鲜活。
- **不保证发现所有错误**：它依赖已记录的剧情事实和结构化信息，替代不了通读正文。
- **不强制全程开启**：默认关闭，需要时开。
- **不依赖其他插件**：可独立安装使用。

它不是替你管理整本小说的作者代理，只是把那些容易被 AI 擅自决定、又容易在长篇里遗忘的事情交还给你。

## 常见问题

### Q1：拍板会不会改我的正文？

不生成、不改写正文，只负责剧情决策和写后结构核对。发现不一致时指出问题，怎么改由你定（唯一的写操作是 `/beat revert`：截断正文到某段起点，且要你主动执行）。

### Q2：需要联网吗？

插件本身不联网，也不上传正文或账本，只读写你工作区里的账本文件。需要联网的是模型服务本身，那是 Harness 和你接的模型的事。

### Q3：账本存在哪里？

`<工作区>/.dsh-novel-beat/<书名>/book.json`，全书共用一份，不是每章的临时笔记。备份或迁移小说时要连账本一起带走。升级到 0.7 时旧账本自动迁移，原文件备份为 `book.json.bak`。

### Q4：剧情没拍完，能不能硬写？能不能整章写完再问？

判定只看一件事：这一章还有没有**问了没答**的岔路。有 → 写正文的工具调用被引擎拒绝（`PENDING_DECISIONS`）；没有 → 放行（包括「这一章刚开始、一个字都没登记」的开场）。

「先写完整章再回头问」不行，0.7 有两道写作单元闸：

| 报错 | 含义 | 怎么处理 |
|---|---|---|
| `write-ahead` | 正文里有没登记成段落的字 | 先 `beat_segment` 登记上一段，或删掉多写的 |
| `unit-gap` | 这一段没接在拍板时的位置上 | 从锚点开始登记，别跳过中间的正文 |
| `prefix-rewritten` | 已登记的正文被改过 | 先 `/beat revert` 回到改动处，或把改动退回去 |
| `gate-mismatch` | 这一段挂的是别的决策 | 一段只对应它自己那一次拍板 |

`beat_verify` 还会给两条只提醒不拦的节奏诊断：`coarse-unit`（一段占了大半章）、`thin-forks`（整章很长却只问了一两个岔路）。

### Q5：短篇也用得上吗？

可以。短篇里涉及身份揭露、背叛、秘密曝光或关键承诺时同样需要你提前决定。但短篇通常不需要维护大量跨章记录，故事简单时直接写更方便。

### Q6：会不会和其他写作插件冲突？

不依赖其他 DSH Novel 插件，可独立运行；主要用 `beat_*` 工具和自己的 `book.json`，不要求别的插件接管正文或共享内部状态。同时装多个写作插件时，仍需留意 Harness 的工具注册、命名冲突，以及各插件对同一剧情事实的处理方式——能否无冲突协作，不能仅凭「独立安装」就保证。

## 技术信息

面向开发者和想了解内部流程的用户。

| 项目 | 内容 |
|---|---|
| 插件名称 | dsh-novel-beat |
| 中文名称 | 拍板 |
| 运行环境 | DeepSeek Harness |
| 工具数量 | 11 个 `beat_*` 工具（0.7 起） |

| 默认状态 | 关闭 |
| 独立运行 | 是 |
| 正文生成 | 不负责 |

11 个工具的参数、调用条件与返回结构见 [`docs/tools.md`](./docs/tools.md)；账本字段、事件流与只读服务见 [`docs/architecture.md`](./docs/architecture.md)。

### 数据在哪

```text
<工作区>/.dsh-novel-beat/<书名>/book.json
```

单文件账本（schemaVersion 2），包含 decisions / canon / obligations / chapters / segments / revisions / requests / tasks / forks / audit。

### 设计原则

- 作者确认优先于模型推测。
- 已确认的剧情事实不能被随意改变。
- 未完成的剧情义务需要持续保留。
- 写作中的实时决策与写后结构核对分开处理。
- 结构核对不越权评价文学质量。
