
## 八、P0/P1：评审的优先级落地（2026-11-15）

依据 `docs/v0.7.0-chatgpt-review-result.md` 的优先级：**P0 修 drift 自动截断风险 → P1 `/beat fork`**。

### P0：回退不再"漂移也硬截"

原实现：正文被手工改过时，`beat_revert` 只加一条 `drift:` 警告，照样按旧 offset 截断——旧 offset 已经
不对应段落边界了，这一步可能截掉作者改过的内容。评审判定这是危险设计。

现在的三档：

| 情形 | 行为 |
|---|---|
| 段落区间 hash 完全对得上 | 直接回退 |
| 被改过，但按登记时的快照原文能在正文里唯一定位到新位置 | 拒绝一次并返回新位置，须 `confirm:true`（命令 `/beat revert 3!`）才动手 |
| 被改过，原文也找不回来 / 同一段原文出现多次 | `cannot-locate`，正文与账本一个字都不动 |

实现要点：
- `locateSegmentText()` 读 `revisions/<id>.md` 快照当锚点（不需要 CRDT 或行级 diff）。
- 唯一定位成功时返回 `relocated:<seg>` 警告，`nextOffset` 用新位置。
- 找不到就 `fail('cannot-locate', …)`，不再有"警告一下然后硬截"。

### P1：作者主动插岔路（`beat_fork` / `/beat fork`）

作者比模型清楚哪里该有岔路。所以给作者一个入口：

1. `/beat fork 要不要当场杀掉独孤博`（或模型用 `beat_fork`）→ 记进 `book.json` 的 `forks[]`，
   `status:'open'`、`id:'f-0001'`。
2. 有 open 岔路时，`beat_next` 拒发新题（`fork-required`），`beat_plan` 不带 `forkId` 也拒。
3. 模型必须 `beat_plan(dir, book, chapter, forkId:'f-0001', beats:[2–4 个选项])` → 岔路变 `planned`、
   挂上 `decisionId`，然后 `beat_next` 才继续。
4. `beat_list(chapter)` 会列出本章 open 的岔路，作者能看见模型有没有理会。

账本兼容：`forks` 是**可选字段**，老账本没有也照读；`/beat off` 时不注册工具、不写 `forks`。

证据：`test/fork.test.mjs`（3 例）+ `test/segment.test.mjs` 的回退三例；`& 'D:\node.exe' --test`
**117 tests / 117 pass**。
