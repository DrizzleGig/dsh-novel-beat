# 给 ChatGPT 的评审稿（v3，可直接整段粘贴）

> 用途：拿第二意见。把「===粘贴区===」之间的内容整段贴给 ChatGPT。
> 背景：作者已用他本人的 ChatGPT 客户端做过几轮讨论（历史会话：插件设计方向 / 小说插件开发计划 / 架构评审结论 / 设计v3优先级），此稿是 v3 实现之后的追问。

===粘贴区===

我在开发一个 DeepSeek Harness 插件 `dsh-novel-beat`：作者写长篇小说时，模型每遇到一个"会改变故事走向的岔路"，插件替它向作者提问（2–4 个选项），作者拍板后写进全书账本（book.json：decisions / canon / obligations / segments / revisions），模型再按答案继续写下一段。

已冻结的原则：
1. 插件只控制"剧情决策"，不控制全部写作（正文仍由模型用 write 直接写文件）；
2. 作者拥有关键剧情选择权，模型无代签权；
3. 引擎层强制（工具守卫 / 常驻系统提示段 / 技能按会话注册），技能只负责引导；
4. 回退依据 = revision_id + 文件 hash + 段落 offset 锚点 + 快照。

现状（v0.7.0，未发布，112 个单元测试全绿）：
- 账本 schemaVersion 2，段落记录 `{id, decisionIds, file, offsetStart, offsetEnd, hash, chars, status, revisionId}`。
- 10 个工具：beat_plan / beat_next / beat_segment / beat_revert / beat_gate / beat_compile / beat_verify / beat_adjust / beat_list / beat_decide。
- `beat_next` 由插件自己调宿主的 userQuestions 服务问作者（不经模型转述），一次只问一个；上一条已拍板但还没 `beat_segment` 登记时拒发下一题（错误码 segment-required）——这就是"写一段、问一个"的硬节奏。
- guard 在引擎层拦 write/edit/apply_patch/str_replace_editor：目标文件能认出"第 N 章"且该章还有没问的岔路时拒绝（PENDING_DECISIONS），其余放行。

作者第二轮实测提了 5 个问题（原话要点）：
1. 两次提问之间的正文不可见——"生成的内容要能够被用户看到，而不是记录在自己的储存中"；
2. 回退"没有发现这个功能"——对刚生成的这段不满意，想退掉重写；
3. "一个章节的内容，怎么可能一个决策点、岔路都不出现？"（他反对允许整章不问就放行）；
4. "一章询问数量基本在三个，这个事情怎么能是固定的？"要求讲清决策点的判断机制，并认为岔路不会特别少；
5. 提问卡片里选项重复显示了一遍。

本轮已实现（v3）：
A. `beat_plan` 一次只收 1 条决策，多给直接报 one-at-a-time；描述改成"走到那个岔路才登记"，掐掉"按章批量规划"。
B. 可见性：`beat_segment` 登记成功后，卡片回显这一段正文（最多 600 字预览 + 总字数 + hash 前 8 位）。
D. 回退：`beat_revert` 改为级联——"退第 N 段"= 正文截断到它的 offsetStart，第 N 段及其后所有已登记段落一起作废，canon/义务按段倒序还原，写一条 revision；返回消息直接说"从第 X 字处重写这一段"。作者侧加了 `/beat list`（列本章段落）与 `/beat revert [段号]`。
F. 卡片 detail 不再拼选项，选项只走 options。
另外修了两个坑：作者在卡片里自己写的答案（status=answered）原先永远到不了 committed（死锁），现在 `beat_decide` 允许为它补结构化 changes；evidence 匹配做了归一化（NFKC、去标点空白、大小写），只吃掉排版差异。

评审后被否决的做法（请判断否决得对不对）：
- C「第 2 段起 decisionIds 不能为空 + 真过渡段每章一次配额」：否决理由是它把"这是过渡段"从叙事判断变成违规，模型最便宜的规避是造一个假岔路（"先吃饭还是先练功"）来解锁，反而制造假决策污染 canon；而且配额会教模型去管理配额而不是去读故事。
- 正文一律走 `beat_segment(text)` 上传、禁止直接 write 正文：会造成"聊天里一份、文件里一份"的双正文，且守卫只按工具名拦，shell 重定向仍可绕过。
- 开场上限 800 字：岔路是事件属性不是字数，阈值会诱使模型在阈值附近造一个假岔路。
- 文案写"一章 5–20 个岔路"：数字锚定会让模型停在 5。

现在的真实数据：这本书第 1 章 5 条决策，第 2–10 章**全部恰好 3 条**，且每章第三条几乎都是"章末留下什么钩子"——是章级模板（开局/中段/章末钩子），不是岔路密度。

请回答（中文，分点，直接给判断，不要客套）：
1. 现在这套"段尾岔路 + 级联回退 + 卡片回显 + 一次一问"，能真正解决作者 5 问吗？哪一条还会让他觉得"这插件在挡我"？
2. 在不设硬门槛的前提下，"每章恰好 3 个"会不会自我维持？成本最低、又不会诱导造假的密度信号是什么？
3. 级联回退在"作者手工改过正文"之后还安全吗（当前只给 drift 警告、照退）？在不引入 CRDT/行级 diff 的前提下，有没有更稳的锚？
4. 段粒度：我把"段 = 已定稿正文，岔路一律落在段尾，答案只作用于下一段"写成了定义。这个定义站得住吗？有没有更不容易被模型误解的说法？
5. 如果只能先做三件事（候选：段落卡片上的「重写这一段」按钮、`/beat fork` 让作者主动插一个岔路、直接发布 0.7.0），你排哪三件？为什么？
