## 二、从样本里拿到的规律

1. **卡片不解释机制。** 最热的这批要么一句话（Study-Mate 23 字、agent-teams 4 个词），要么列 3–6 个用户看得见的动作。没有一个从「七个 beat_* 工具」讲起。
2. **卡片第一句要有身份或画面。** 「你的AI学习搭档」「让 AI 伙伴自己起个话头」——读者先认出"这是给我的"，才愿意看后面。
3. **README 第一屏只干一件事：让读者认出自己。** image-gen 是 "Draw by talking"；Study-Mate 是一段作者自述（"这是我自己用的东西，文档写得太像 AI"）。
4. **一张「没有它 / 有它」的对比表，比十条功能更能说明价值。**（Study-Mate 的 Why Use It 三列表）
5. **一张「你说什么 → 它做什么」的对话表，让读者看到自己会怎么用。**（image-gen 的 Just say it）
6. **主动写「不适合谁」和「它不做什么」。** Openwrite、novel-forge 都写；可信度来自边界，不来自形容词。
7. **三步安装，命令可复制，技术信息沉底。**

AI 替你写的剧情，真的是你想要的吗？「拍板」让你决定关键走向，再让 AI 继续写。

### 极短版（25 字内，副标题 / 宣传语用）

AI 写正文，关键剧情你拍板。

### 标准版（86 字，平台要求长描述时用）

AI 写小说时，可能擅自决定关键剧情，也容易忘记人物关系、秘密和承诺。「拍板」会在写作过程中拦截重要剧情岔路，提供不同走向及其代价，由作者决定后继续写；写完再核对剧情变化。

1. AI 可以替你写故事，但不能替你决定故事怎么走。
2. 让 AI 负责写，让作者负责决定。
3. 每个重要剧情，都应该经过作者同意。

## 四、README 全文（ChatGPT 文本）

````markdown
# DSH Novel Beat｜拍板

> AI 可以替你写故事，但不能替你决定故事怎么走。

你让 AI 写一章，主角去拍卖会买下一块玉佩。

AI 写得很顺：有人认出了玉佩，有人揭开了主角的身世，两个原本敌对的势力突然有了联系。

三千字写完，剧情看起来推进了不少。

但你发现：你根本没打算这么写。

你原本想让玉佩成为一条慢慢展开的伏笔，结果 AI 直接揭开了秘密。更麻烦的是，写到后面，AI 还可能忘记谁知道这个秘密、谁答应过什么、玉佩现在究竟在谁手里。

**「拍板」就是用来处理这些关键剧情决定的。**

它在 AI 写正文之前，把重要的剧情岔路摆出来，让你选择；正文完成后，再检查这一章有没有落实已经决定的剧情。

## 没有拍板 / 有拍板

| 没有拍板 | 有拍板 |
|---|---|
| AI 自己决定谁发现了秘密 | 先让你决定秘密由谁发现 |
| AI 自己安排人物立场变化 | 先比较不同立场变化的后果 |
| AI 可能忘记之前的承诺 | 把尚未兑现的承诺留在全书记录中 |
| AI 可能擅自转移关键物品 | 核对物品归属有没有被错误改变 |
| 写完只能自己逐段检查 | 写完核对关键剧情变化 |
| 下一章重新解释前面的剧情 | 下一章可以沿用这本书的剧情记录 |

它不是让 AI 少写一点，而是让 AI 在重要剧情上少替作者做主。

## 你会怎么用它

「拍板」不需要一直开启。

普通章节、日常对话、过渡场景，你可以继续使用原来的写作方式。

当你准备写一章涉及重要剧情变化的内容时，再开启它。

### 作者会说的话 → 拍板会做什么

| 作者会说的话 | 拍板会做什么 |
|---|---|
| 这章主角要拿到一件重要物品，但后续怎么发展还没决定。 | 找出可能改变故事走向的节点，提供不同选择。 |
| 这个秘密暂时不能让所有人知道。 | 把秘密的知情状态作为需要确认的剧情变化。 |
| 这两个人到底要不要合作？ | 列出不同关系走向及其后续影响。 |
| 上一章答应的事情，这章要兑现吗？ | 提醒尚未完成的承诺和义务。 |
| 这章写完了，帮我看看有没有漏掉之前决定的事情。 | 核对已确定的剧情变化有没有落实。 |
| 下一章开始之前，先看看目前有哪些事情没解决。 | 摆出这本书已经确定的事实和未完成的剧情义务。 |

## 它怎么工作

整个过程分为三个阶段。

### 01. 写之前：把剧情岔路摆出来

例如，你正在写一章：

> 林砚在拍卖会上拍下了一块来历不明的玉佩。

这件事可能带来几个重要变化：

- 谁认出了玉佩？
- 林砚是否因此暴露身份？
- 有没有其他势力开始关注他？
- 玉佩是否会引出新的交易或承诺？

「拍板」会将需要作者决定的节点提出来。

例如：

**谁会认出玉佩？**

- **选择 A：没人认出。** 玉佩继续作为伏笔，暂时不引入新的冲突。
- **选择 B：一位老者认出。** 获得一条身世线索，但林砚可能被暗中关注。
- **选择 C：竞争对手认出。** 双方产生新的冲突，但也会提前暴露对方掌握的信息。

每种走向都有不同的代价和后续影响。

你可以选择其中一种，也可以根据自己的想法调整。

选择权始终属于作者。

### 02. 写作过程中：让之前的决定继续有效

作者确认的剧情决定，会记录在这本小说共用的账本里。

例如：

- 玉佩目前由林砚持有。
- 老者已经认出玉佩。
- 林砚还不知道玉佩的真实来历。
- 老者答应提供进一步线索。
- 这项承诺尚未兑现。

下一章开始之前，可以重新提供这些记录。

这样，AI 不需要每次都重新猜测人物关系和剧情进度。

已经确定的事实有据可查，尚未完成的事情也不会轻易消失。

### 03. 写完之后：核对剧情有没有落实

正文完成后，「拍板」会检查这一章的关键变化。

例如：

- 已经决定老者认出玉佩，这件事有没有发生？
- 已经决定玉佩由林砚持有，有没有被错误转移？
- 老者尚未兑现的承诺，有没有被正文错误地写成已经完成？
- 有没有出现与已有剧情事实冲突的内容？

发现不一致时，会指出问题，交给作者判断和处理。

它不会擅自修改正文，也不会替作者改变已经确认的剧情。

## 适合谁 / 不适合谁

**适合**

- **日更网文作者**：章节多、更新快，需要减少前后剧情矛盾。
- **长篇连载作者**：人物关系复杂，有大量秘密、承诺、交易和长期伏笔。
- **AI 辅助写作的作者**：希望 AI 提高写作效率，但不希望 AI 擅自决定关键剧情。
- **重视人物与剧情连续性的作者**：不希望人物立场和已经发生的事情随着章节推进而随意改变。

**不适合**

- 只想让 AI 直接生成正文，不关心剧情选择过程的作者。
- 只写短篇、日常对话或简单场景，不需要长期维护剧情状态的作者。
- 希望插件自动判断剧情是否精彩、人物是否鲜活、文笔是否优秀的作者。

「拍板」不是所有章节都必须使用的工具。

它只在重要剧情需要作者决定时发挥作用。

## 怎么开始

只需要三步。

### 第一步：安装插件

在 DeepSeek Harness 里执行：

```powershell
dsh plugin --profile web add dsh-novel-beat
```

或从 GitHub 安装：

```powershell
dsh plugin --profile web add github:DrizzleGig/dsh-novel-beat
```

它可以独立使用，不需要安装其他 DSH Novel 插件。

### 第二步：开启拍板

默认关闭。

在需要时输入：

```
/beat on
```

也可以点击输入框旁的拍板按钮开启。

不需要拍板的章节，继续使用原来的写作流程即可。

### 第三步：决定剧情，继续写作

让 AI 先整理这一章的重要剧情节点。

阅读不同走向及其代价，选择你认可的方向。

确认后继续写正文。

正文完成后，再进行一次结构核对。

从这一章开始，重要的剧情决定就可以持续记录到整本小说中。

## 它不做什么

「拍板」有意保持一个明确的职责范围。

- **不写正文**：它不是正文生成器，不接管你的写作模型和写作流程。
- **不替作者拍板**：它提供选择和后果，最终决定由作者完成。
- **不擅自改变事实**：不会把模型猜测直接当成已经发生的剧情事实。
- **不评价文笔**：写后校验只检查结构和状态，不判断文笔、情绪、节奏、人物塑造是否优秀。
- **不保证发现所有错误**：校验范围受已有记录和结构化信息限制，不能代替作者通读正文。
- **不强制全程开启**：默认关闭，由作者决定什么时候使用。

它不负责让 AI 写出更漂亮的句子。

它负责让 AI 不要在关键剧情上替作者做决定。

## 技术信息

以下内容面向希望了解插件内部工作方式的开发者。

### 项目名称

- English：dsh-novel-beat
- 中文：拍板
- 运行环境：DeepSeek Harness
- 项目定位：小说剧情决策与结构一致性检查插件
- 独立性：不依赖其他 DSH Novel 插件

### 七个工具

| 工具 | 职责 |
|---|---|
| `beat_plan` | 识别章节中需要作者决定的关键剧情节点，每个节点给 2–4 个真分叉 |
| `beat_list` | 看全书概览或本章节点；`context:true` 返回 canon + 未回收义务 + 最近决策 |
| `beat_decide` | 记录作者选择；改主意用 `supersede:true` + `reason` |
| `beat_gate` | 写正文前体检；还有未拍板就返回 `pass:false` |
| `beat_compile` | 产出本章约束（必须发生、证据、不得出现、既有义务、全书 canon） |
| `beat_verify` | 写后校验：缺变化 / 踩禁项 / 到期义务没回应，都会给出 failure 或 warning |
| `beat_adjust` | 作者主权动作：`waive` 义务、`supersede` 决策，必须写 `reason` |

### 写作门控

当必要的剧情决策尚未完成时，`beat_gate` 会返回：

```
pass: false
```

表示当前写作流程尚未通过决策检查。门控的作用是确保重要剧情选择得到处理，而不是评价正文质量。

### 全书账本

使用 `book.json` 保存全书共用的剧情记录，主要包含：

- `canon`：已经确立的剧情事实。
- `obligations`：尚未完成的承诺、债务、约定和其他剧情义务。

这些记录可以跨章节使用，为后续剧情决策和结构核对提供依据。

### 核心设计原则

- 作者确认优先于模型推测。
- 已确认的剧情事实不能被随意改写。
- 未完成的剧情义务应当持续保留。
- 决策和校验分开处理。
- 结构校验不越权评价文学质量。

让 AI 帮你写，但故事始终由你掌控。

DSH Novel Beat · 拍板
````
