## 一、一句话结论

v0.7.0 不做"功能更多的工作流"，而是把 Beat 从**依赖模型自觉的工具集**改造成**由 Engine 掌管状态、权限与作者授权的决策事务引擎**：
**开着就一定走流程，一次只问一个决策，作者亲手落账，写完可回退，一本书一本账，且不装任何兄弟插件也能独立跑完一整章。**

v0.6.1 的 7 个工具、`/beat on|off|status`、`book.json` 账本语义保留；新增的是**执行层（guard）、事务层（request/response receipt）、映射层（segment/revision）、回退层（revert）**。

## 二、与 v0.6.1 的差异总表

| 维度 | 0.6.1 现状 | 0.7.0 定稿 |
|---|---|---|
| 触发 | `/beat on` 只是把工具放出来；技能全局注册且写着"默认关闭"；模型可完全不理 | 模式开启 = 技能按 agent 层注册 + 常驻规则段注入 + 写入 guard 生效；模式关闭 = 三者全撤 |
| 提问节奏 | `beat_plan` 一次登记最多 20 个决策，模型常一次问完再写 | `beat_plan` 只登记（`proposed`），`beat_next` 一次推动**一个**决策到作者面前；每拍板一次写一段 |
| 作者授权 | `beat_decide` 不校验是否问过作者，模型可代签 | **Response Receipt**：`request_id` 由插件调用 `userQuestions.ask()` 亲手发放并核对，模型无法伪造 |
| 正文映射 | 无 | `beat_segment`：decision ↔ 文件/锚点/hash/字数，一个 segment 可覆盖 2–3 个强耦合决策（原子决策组） |
| 回退 | 无 | `beat_revert`：按 `revision_id` + 文件 hash + HTML 注释锚点回退段，canon/obligations 一并回退，冲突则拒绝 |
| 闸门 | `beat_gate` 看整章 pending 是否为空 | 闸门下沉到**本段**：本段涉及的决策全部 answered+committed 才放行 |
| 账本位置 | `bookDir(dir, book)` 直接用调用方传入的 cwd → 同一本书可能裂成多本账 | 工作区根锚定 + 书名 sanitize + 多账本探测与合并 |
| 数据结构 | schemaVersion 1 | schemaVersion 2（新增 `segments[]`/`revisions[]`/`requests[]`/`tasks[]`，`decisions[]` 加状态字段） |
| 相邻插件 | 无契约，只靠读 book.json | 对外暴露 `novelBeat` 服务（查询/订阅）+ `docs/adapter-contract.md`；fade 现有"读 book.json 的 canon/obligations"路径继续有效 |
| 工具数 | 7 | 9（+`beat_next`/`beat_segment`/`beat_revert`，`beat_decide` 保留为兼容薄别名，见 §六） |

## 三、五条冻结原则（承接讨论稿 §九，不再改）

1. **Beat 控制决策，不控制全部写作。** 它管"剧情分叉必须由作者拍板"，不管语气、节奏、修辞。
2. **作者拥有关键剧情选择权，模型无代签权。** 任何进入 canon 的 `changes` 必须能追到一次作者亲手作答。
3. **Engine 控制权限，Skill 负责引导。** 能否调用工具、能否写正文由插件代码判定；SKILL 只教模型"怎么用"。
4. **Revision 是回退依据，Segment 是正文映射，Message 是审计证据。** 三者不混用。
5. **Beat 拥有剧情决策权威，Conductor 只有任务调度权。** 编排器不能替作者拍板，也不能推翻已确认事实。

## 四、架构

### 4.1 三层强制（P0）

| 层 | 手段 | 生效条件 | 失效后果 |
|---|---|---|---|
| L1 引导（软） | SKILL 仅在 `mode=on` 时按 agent 作用域注册；描述首行写"已开启：本次写作必须…" | agent 层 | 模型不看技能也不影响正确性 |
| L2 规则（中） | `systemPrompt.section({ name:'novel-beat', order:60, text: f(scope) })`，`mode=off` 返回空串 | 每步组装时 | 规则始终在场，不依赖模型检索技能 |
| L3 权限（硬） | `tools.guard()` 拒绝越权写入 + 工具 `when` 门控 | 每次工具调用前 | 模型无法先写正文再补拍板 |

L2 的文本函数按 `scope`（即 agent）读模式缓存，因此同一进程里不同会话互不影响。
L3 的 guard **注册在插件根 ctx（全局层）**，函数内部按 `execution.agent.id` 查模式缓存决定是否拦截——M0 已验证 agent 作用域为根作用域、彼此不继承，若注册到 `agentCtx` 则子 agent 不受保护（见 `docs/v0.7.0-M0-report.md` §二.1）。决策依据是 `execution.agent.id` + `execution.name` + `execution.arguments`，同步判定，不读盘；解析相对路径用同步的 `workingDirectory.get(execution.agent.session)`。

**已知边界（必须写进 README 的"能做到什么/做不到什么"）：**
- guard 只能看见结构化文件工具（`write` / `edit` / `apply_patch` 一类，参数里带路径）。`pwsh` 里的重定向、第三方工具写盘**拦不住**。
- 对策：`beat_verify` 与 `turn/end` 后的**漂移检查**（正文 hash 与 segment 记录不符即 warning + 建议 `beat_revert`）。也就是说：硬拦结构化写入，事后核验一切写入。
- guard 的**跨会话覆盖**：M0 已验证全局 guard 的判定链是 `[global, ...scopeChainOf(agent)]`，agent 作用域为根（互不继承）。因此 v0.7.0 采用"**根 ctx 注册一个全局 guard + 函数内按 `execution.agent.id` 判模式**"，主会话与子 agent 一并受保护；模式未开启的会话原样放行。

### 4.2 两套状态机（绝不混用）

**决策状态（decision）**
```
proposed ──beat_next 取到──▶ asked ──作者作答──▶ answered ──落账──▶ committed
   │                                                        │
   └──────────── superseded（被后续决策取代）◀──────────────┘
                                                              
另有 cancelled（作者放弃该分叉）
```
- `proposed`：已登记，含 2–4 个候选与各自 changes/obligations/forbidden。
- `asked`：已发出 `request_id` 并等作者；同一时刻**全书最多一个** `asked`（串行保证）。
- `answered`：收到作者答案（`selected` 或 `custom`），尚未写 canon。
- `committed`：canon/obligations 已落账，且（若绑定了 segment）正文锚点已登记。

**创作任务状态（task）**
```
created → planning → awaiting_author → writing → segment_committed → verifying → completed
                                     ↘ blocked（canon 冲突/缺正文/作者中止）
```
task 是"这一章/这一段正在进行的工作单元"，`beat_plan` 创建，`beat_segment` 推进，`beat_verify` 收尾。

**五个 ID 各管各的**：`decision_id`(`b3-2`) / `task_id`(`t-0007`) / `segment_id`(`s-0012`) / `revision_id`(`r-0009`) / `request_id`(`q-1f3a9c`)。

### 4.3 一次决策的完整时序（v0.7.0 的主循环）

```
作者：「写第三章」
模型：beat_plan { book, chapter:3, beats:[…全部决策点与选项…] }
      → 账本新增 b3-1…b3-5，状态 proposed，task t-0007=planning
模型：beat_next { book, chapter:3 }                     ← 一次一个
      → 引擎取 b3-1，状态 asked
      → 引擎自己调 userQuestions.ask() 把选项卡片推给作者（含 canon 当前值）
      → 作者点「B. 让他在雨里等她」
      → 引擎落账：b3-1=committed，canon 更新，obligations 新增，发放 request_id=q-1f3a9c
      → 返回：{ request_id, decision_id:'b3-1', chosen:'B', changes:[…], canonBefore:[…] }
模型：write/edit 写这一段的正文（本段对应 b3-1 无 pending，guard 放行）
模型：beat_segment { book, decisionIds:['b3-1'], file:'正文/第003章.md', anchors:[…] }
      → 记录 fromMarker/toMarker/hash/chars，segment s-0012=committed，task=segment_committed
模型：beat_next { … }                                    ← 下一段
…… 循环到本章最后一个决策 ……
模型：beat_verify { book, chapter, file } → 核对 hash/锚点/canon 一致性
模型：beat_compile { book, chapter } → 章末汇总（保留 0.6 语义）
```

**作者口头拍板的路径**：作者已在聊天里说"选 B"，模型调 `beat_next { answer:'B' }`；引擎**仍然发一张确认卡**（"你选了 B，确认落账？"），作者一次点击完成落账。模型提供的答案只是预填，落账凭据仍然是作者点击。

**校验规则（`validateBook` 升级）**
- `schemaVersion` 只接受 2；读到 1 触发迁移。
- `decisions[].status` 必须在枚举内；`committed` 必须有 `requestId` 且 `requests[]` 里有对应条目（**防伪造的第一道闸**）。
- `segments[].decisionIds` 每项必须存在；同一 decision 只能被一个未回退的 segment 引用。
- `canon` 的 `(entity,key)` 唯一（保留）；`obligations.id` 唯一（保留）。
- `requests[].id` 唯一；`answeredAt` 非空才算有效凭据。

**写盘**：沿用 0.6 的 tmp → `.bak` → rename 原子写 + per-book 串行锁，不引入任何第三方依赖。

## 六、工具契约（v0.7.0 共 9 个）

所有工具仅在 `mode=on` 时注册（`when: modeCache.get(sessionKey(ctx)) === true`）。关闭时 `restrict({deny})` 兜底。

| 工具 | 状态 | 作用 | 关键参数 | 失败码 |
|---|---|---|---|---|
| `beat_plan` | 改造 | 登记一章的决策点（1–20 条，每条 2–4 选项），全部 `proposed`；创建 task | `book, chapter, beats[], file?` | `empty-beats` `too-many-beats` `bad-option` `duplicate-changes` |
| `beat_next` | **新增** | 推进**一个**决策到作者面前并落账：取 `proposed`→问作者（引擎内联 `userQuestions.ask`）→写 `origin:author` 凭据→`committed`。**一次只问一个**，且上一条还没 `beat_segment` 登记时拒发下一个（`segment-required`） | `book, chapter` | `no-user-questions` `one-at-a-time`（传了 `ids`）`segment-required` `no-book` `ask-failed` `canon-conflict` |
| `beat_segment` | **新增** | 登记本段正文位置与 hash，绑定 decision↔segment（`decisionIds` 可为空=开场/过渡段，须给范围） | `book, chapter, decisionIds[], file, excerpt?, fromMarker?, toMarker?` | `no-decisions`（空 ids 又没给范围）`not-committed` `already-segmented` `excerpt-ambiguous` `excerpt-not-found` `empty-segment` |
| `beat_revert` | **新增** | 按 revision 回退段：截正文 / 撤 canon 义务 / 两者；纯 `ledger` 回退不受"必须从最后一段退"限制 | `book, chapter, segment?, mode:'text'\|'ledger'\|'both', force?` | `nothing-to-revert` `not-last` `drifted` `bad-mode` |
| `beat_gate` | 改造 | 本段闸：本段涉及的决策全部 committed 才放行（不传 `ids` 则按整章） | `book, chapter, ids[]?` | —（返回 `pass`/`pending`） |
| `beat_decide` | 降级 | **只在宿主没有提问服务时兜底**；有 `userQuestions` 时直接 `use-beat-next` 拒绝，防止模型绕过内联提问 | `book, chapter, id, choice` | `use-beat-next` |
| `beat_adjust` | 保留 | 登记字级/非剧情修订（不新增决策），写 revision 并更新 segment hash | `book, decisionId?, file, note` | `no-segment` |
| `beat_compile` | 保留 | 章末汇总：已拍板清单、canon 变更、未偿 obligations | `book, chapter` | `no-book` |
| `beat_verify` | 改造 | 读正文核对：hash、锚点、canon 一致性、漂移检测 | `book, chapter, file` | `hash-mismatch` `anchor-missing` |
| `beat_list` | 保留 | 状态总览（书/章/决策状态/未偿义务/段落） | `book?, chapter?` | `no-book` |

> 表中 10 行是因为 `beat_decide` 是兼容别名；对外宣称 9 个主工具。

**为什么撤销讨论稿里的 `beat_ask`**：`beat_next` 在引擎内部直接调用 `userQuestions.ask()`，一个问题一次调用即可完成"取题→问→落账"，比"`beat_ask` 发号 + 模型转述 + `beat_decide` 核销"少一圈往返，且 receipt 由同一处生成与消费，更难伪造。若 M0 验证发现工具执行中嵌套提问不被允许，则回退到讨论稿的三步方案（`beat_ask`/`beat_decide`），接口已按此预留（`beat_decide` 保留）。

## 七、执行层规则表（guard）

**只在 `mode=on` 时生效**，判定顺序固定如下（同步、不读盘，账本状态由内存缓存提供）：

0. `execution.agent` 为空 → 放行；该 agent 的 mode 非 `on` → 放行（含子 agent：全局 guard 同样按 `exec.agent.id` 判）
1. 工具名不在写入集合内（`write`/`edit`/`apply_patch`/`str_replace_editor`）→ 放行
2. 取出目标路径（`write`/`edit`/`str_replace_editor` 取 `arguments.file_path`，`apply_patch` 解析补丁头里的路径），用 `workingDirectory.get(execution.agent.session)` 解析为绝对路径
3. 目标不在 `bodyRoots` 内、也不是已登记 segment 文件 → 放行
3.5 **按章判**（M2 实测补上的关键一条）：目标文件名里能认出"第 N 章"（`/第\s*([0-9]{1,3})\s*章/`）时，用**第 N 章自己的**决策统计判，而不是账本最后一条决策所在章——否则"第 1–7 章都拍完了，去写全新的第 8 章"会被误判成已放行（这正是 2026-11-14 斗罗会话的真实事故）。文件名认不出章号（如"番外.md"）才退回账本进度，属已知边界。
4. **2026-11-14 作者实测后的修订（节奏版）**：初版的"该章一条决策都没有 → 拒 `NO_TASK`"被删掉了。原因：作者要的节奏是"**先写内容 → 遇到岔路问一次 → 按答案接着写**"，所以"这一章还没登记任何岔路"是合法的开场写作，不是错误。现在的判定只看"有没有岔路没问"：
   - 该章 `open > 0` 且 `awaitingSegment === 0` → **拒绝** `PENDING_DECISIONS`："第 N 章还有 M 个岔路没问。先 beat_next 问下一个（一次只问一个），按作者的选择写完这一段、beat_segment 登记，再问下一个。"
   - 该章刚拍完板、那一段还没登记（`awaitingSegment > 0`）→ 放行（正在写这一段）。
   - 该章还没登记任何决策、或全部问完并登记完 → 放行（`reason: 'ok'`）。
5. `NO_TASK` 的语义因此**只剩下 `beat_verify`**：一章正文一条决策都没有时，不允许盖 `verified` 章（防止整章闷头写完再补账）。
6. 目标是**已登记 segment** 且正文 hash 与记录不符 → 放行但记 `drift` 警告（允许作者手改，`beat_verify` 会要求 `beat_adjust` 或 `beat_segment` 重新登记）；未登记成段落的正文由 `beat_verify` 报 `unsegmented` 警告。

**受保护正文根**：配置项 `bodyRoots`（默认 `["正文"]`），支持 `/beat body <path>` 增删；相对路径按工作区根解析。若配置为空，guard 退化为"只保护已登记 segment 的文件"。

**放行通道**：`beat_adjust`（修订登记）、`beat_segment`（登记段落）、`beat_revert`（回退）三个工具自身写账本，不写正文；正文写入始终由模型的文件工具完成，guard 只看"能不能写"。

## 八、账本锚定与迁移

### 8.1 一本书一本账

## 十二、已拍板结论（2026-11-14，作者确认）

### D1 提问方式 → **取 A：引擎内联提问**
`beat_next` 内部直接 `userQuestions.ask()`，取题+提问+落账一次完成。凭证由同一处生成与消费，模型无法伪造。
**风险与兜底**：依赖"工具执行中可嵌套提问"，M0 第 2 项验证；若被框架拒绝（`DELEGATED_CALLER` / 死锁 / UI 不展示），立即按讨论稿三步方案降级（`beat_ask` 发号 + `beat_decide` 核销），`beat_decide` 已按此预留，属实现级回退，不改本方案的对外契约。

### D2 guard 保护范围 → **取 A：默认只保护 `正文/`**
配置 `bodyRoots` 默认 `["正文"]`，`/beat body <path>` 可增删；配置为空时退化为"只保护已登记 segment 的文件"。一次配置成本换日常零摩擦。

### D3 默认开关 → **取 A：默认关闭**
装上不注册工具、不注入规则、不启用 guard、不占 schema；`/beat on` 后三层强制全量生效。README 与技能描述必须写清"开启后就是硬流程"，不再让"默认关闭"被误读成"开着也能不管"。

### D4 节奏（2026-11-14 22:40，作者实测后口头拍板）→ **取"写一段 → 问一个 → 写下一段"**
作者原话："我想要的是，AI先进行内容创作，遇到第一个决策点，问一次，根据结果继续生成内容，直到遇到第二个决策点，以此类推。"
据此撤销初版的"原子决策组 `ids`"（模型会用它一次问三个），改为：
1. `beat_next` 一次只问一个，传 `ids` 直接拒绝；
2. 上一题没 `beat_segment` 登记成段落时，拒发下一题（`segment-required`）；
3. guard 不再要求"本章先 plan 才能写"，只拦"这一章还有岔路没问"；
4. `beat_verify` 补两条提醒（`drift` / `unsegmented`），并把"一章零决策"挡在盖章之外（`NO_TASK`）。
**原因**：初版把"决策授权"做对了，把"写作节奏"做错了——一次性问完 3 个岔路，等于让作者在还没看到正文时就拍板三处剧情，且模型随后整章一次写完，`beat_revert` 无段落可退（作者原话："关于回退，我并没有发现这个功能"）。
