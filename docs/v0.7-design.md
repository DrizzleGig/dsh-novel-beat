# dsh-novel-beat 0.7 设计稿（讨论用）

> 基于 2026-11-14 对 `D:\斗罗大陆` 会话（session-08878df6，17 轮 / 310 次工具调用）与 0.6.1 源码的审计。
> 本稿是讨论稿，定稿前不改代码。

## 一、审计结论（证据见该会话）

| # | 现象 | 证据 | 根因 |
|---|---|---|---|
| 1 | 开章写作时 beat 不被调用 | T1 加载的是 novel-forge 的 `novel` 技能，全程无 beat 调用 | 技能只是建议；`/beat on` 只把工具放出来（`index.js:126`），没有任何强制 |

## 二、0.7 目标

1. **开着就一定走流程**：模式开启后，写正文前必须有作者拍板，由框架强制，不靠模型自觉。
2. **一次一个决策**：`beat_next` → 问一个 → 拍板 → 写这一段 → `beat_next`，直到章末。
3. **可回退**：任何两个决策点之间的正文与账本都能整体退回重写。
4. **一本书一本账**：账本路径只由工作区根 + 书名决定，与调用方传的 dir 无关。

非目标：不做正文生成、不做文笔评价、不替代 novel-fade 的记忆、不接管会话消息。

## 三、新流程（状态机）

```
chapter_start
  → beat_list(context)                       # 拿 canon / 未回收义务
  → beat_next(chapter)                       # 返回下一个待拍板点，或 {done:true}
      ├─ 有：返回 pending 决策（或提示模型用 beat_open 登记）
      │    → ask_user_question(单个)
      │    → beat_decide(id, choice, changes)
      │    → 写这一小段正文（从上一段的结尾到本决策点之后）
      │    → beat_segment(decisionId, file, from, to)   # 记录片段
      │    → beat_next ...
      └─ 无：beat_compile → 写剩余/整章 → beat_verify → 章末
```

**关键约束**：`beat_next` 未返回 done 前，`write`/`edit` 被 guard 拒绝（见五）。

## 四、工具面变化（7 → 10）

| 工具 | 状态 | 说明 |
|---|---|---|
| `beat_plan` | 改 | `beats` 数组改成单数 `beat`（或 `maxItems:1`）；一次只登记一个 |
| `beat_next` | 新增 | 返回下一个待拍板点；没有则返回 `done:true`（含本段写作提示） |
| `beat_segment` | 新增 | 记录「哪个决策产生哪段正文」：file / fromMarker / toMarker / hash / 字数 |
| `beat_revert` | 新增 | 回退到某个决策之前：后续决策标 stale、回滚 canon、返回切点与重写指令 |
| `beat_decide` | 改 | 必须带 `asked:true` 与作者原话摘要；缺了拒绝（见五） |
| `beat_gate` | 改 | 从「整章闸」改为「本段闸」；章末用 `beat_compile` 做一次总检 |
| `beat_compile` | 保留 | 章末总编译（写出全书约束） |
| `beat_verify` | 保留 | 写后结构核对 |
| `beat_list` | 改 | 返回 canonical 账本路径；发现多账本时警告 |
| `beat_adjust` | 保留 | waive / supersede |

## 五、三层强制（0.7 的核心）

1. **技能层（软）**：技能只在模式开启时注册；技能正文改成单步循环；描述去掉「默认关闭」这种会让模型自我否定的句子，改为「由插件开关控制，开启后必须使用」。
2. **注入层（中）**：`/beat on` 时调 `agent.inject()` 注入一段常驻规则；每章结束时再注入一次，抵消上下文漂移。规则只有四句：
   - 写任何正文前，先 `beat_next`；
   - 拿到决策点，先问作者，再 `beat_decide`；
   - 写完一段，`beat_segment`；
   - `beat_next` 返回 done 之前不写正文。
3. **框架层（硬）**：在 agent 作用域注册 `ctx.tools.guard()`，当本书本章存在 pending 决策时，拒绝 `write` / `edit` / `apply_patch` 一类正文写入工具。guard 是同步的，状态从内存储存器读取，由 beat_* 工具维护。

> DSH 依据（`dsh-doc/references/practices.md`）：`ctx.tools.guard()`「can only deny」，是「必须无条件成立」的拒绝；`agent.inject()` 进入下一个 step；`ctx.systemPrompt.section()` 加常驻提示；`tools/pre-execute` 可返回 `ask`。

## 六、回退设计

`book.json` 升到 schemaVersion 4，新增：

```json
"segments": [
  { "id": "seg-b1-2", "decisionId": "b1-2", "chapter": 1,
    "file": "正文/第1章.md", "fromMarker": "【拍板:b1-1】", "toMarker": "【拍板:b1-2】",
    "hash": "sha256:…", "chars": 860, "status": "written" }
]
```

写作约定：每段开头/结尾留不可见的 HTML 注释标记（`<!-- beat:b1-2 -->`），`beat_segment` 只记标记与 hash，不存正文。

`beat_revert(decisionId)`：
1. 把该决策之后的决策标 `stale`（保留历史，不删）；
2. 回滚这些决策写入的 canon/obligations；
3. 找到该决策对应的 segment 起点，返回 `{ file, cutAt, reason, rewriteBrief }`；
4. 模型据此从切点重写，重写后 `beat_segment` 新片段。

面板（client.js）显示一条可点击的时间线：每个决策一个点，点「退到这里」即调用 revert。

## 七、账本定位

- `bookDir` 改为：工作区根（由 `workingDirectory` 服务取当前 agent 的根）+ `sanitize(book)`；调用方传的 `dir` 只作为「书所在目录」的线索，不参与落盘路径。
- `beat_list` 返回 `canonicalDir`；若同书名在多处存在 book.json，返回 `duplicates[]` 并提示合并。
- 迁移：0.6 的多份账本按「决策最多的一份」为准，其余标 `legacy`。

## 八、迁移与兼容

- `schemaVersion: 3 → 4`，读旧账本自动升级（segments 为空）。
- 工具名不变的不破坏；`beat_plan` 的数组参数保留兼容（内部按 maxItems 1 校验），但文档只讲单数。
- 0.7.0 发版说明：行为变化（单步、强制、回退），数据自动迁移。

## 九、与 ChatGPT 讨论后的定稿（2026-11-14）

判断：0.7 不是「一次一个决策」的工作流升级，而是把 Beat 从一个依赖模型自觉遵守的**工具集**，变成由 Engine 控制状态、权限和作者授权的**决策事务系统**。审计暴露的是三个不同层面的问题——执行权（开启不代表必须使用）、决策权（模型能替作者定）、连续性（决策与正文无可靠映射），三者不能只靠 Skill 规则解决。

### 9.1 五条设计原则（冻结）

1. Beat 控制决策，不控制全部写作。
2. 作者拥有关键剧情选择权，模型没有代签权。
3. Engine 控制权限，Skill 负责引导模型。
4. Revision 是回退依据，Segment 是正文映射，Message 是审计证据。
5. Beat 拥有剧情决策权威，Conductor 只有任务调度权。

### 9.2 对五个待定问题的结论

| 问题 | 结论 |
|---|---|
| 单步会不会切碎文风 | 保留单步，同时增加**原子决策组**：2–3 个强耦合、无法分开拍的决策可作为一个事务一次拍板，但仍是一次提问、一次确认 |
| guard 拒绝粒度 | 拒绝落在**真正执行文件写入的底层入口**，不是只管 Beat 自己的工具；按「段」判断（pending 决策对应下一段），作者只想改错字时走 `beat_adjust` 放行，不进写作闸 |
| 回退依据 | `revision_id` + 文件 hash + HTML 注释锚点；会话消息 id 只作审计证据，不作为回退依据（跨 fork 会漂） |
| `asked:true` 能否防撒谎 | 不能只靠布尔值。改为 **Author Request / Response Receipt**：`beat_ask` 发起请求拿到 `request_id`，`beat_decide` 必须带上 `request_id`，由插件核对该请求确实存在且已回答，否则拒绝 |
| 是否砍 `beat_gate` | 不砍。`beat_next` 是「下一段该问什么」，`beat_gate` 是「本章写作闸」，章末仍需闸门；但闸门从「整章 pending 为空」改为「本段无 pending」 |

### 9.3 两套状态必须分开（架构修正）

- **决策状态**：`proposed → pending → asked → answered → committed`
- **创作任务状态**：`created → planning → awaiting_author → writing → segment_committed → verifying → completed`

一个章节可能同时有 5 个已确认决策、3 个已完成场景、1 个正在写的场景、1 个未解决决策；把这些塞进一个状态字段，Conductor 就无法正确调度。

**五个 ID 各管各的**：`decision_id`（决策生命周期）、`task_id`（创作任务）、`segment_id`（正文片段）、`revision_id`（文件版本）、`request_id`（作者授权）。

### 9.4 开发优先级（Roadmap）

| 阶段 | 内容 | 说明 |
|---|---|---|
| **P0 强制执行层**（最高优先级） | Skill 仅在模式开启时注册；`agent.inject` 注入强制规则；`tools.guard` 在 pending 时拒绝越权写作；模式关闭时撤销工具权限 | 不解决这一层，后面所有功能都建立在「模型愿意遵守」的沙地上 |
| **P1 单步决策事务** | `beat_next`、`beat_ask`、`beat_decide`、Author Request / Response Receipt、原子决策组 | |
| **P2 段落映射** | `beat_segment`、Segment ID、Decision ↔ Segment 多对多、Revision ID + 文件 Hash | |
| **P3 安全回退** | `beat_revert`、HTML 注释锚点、Branch 隔离、Stale 传播、Canon 依赖核验 | |
| **P4 章末编译与验证** | `beat_compile`、`beat_verify`、检查决策是否落实、正文与 Canon 冲突、未授权剧情是否进入正文 | |
| **P5 Conductor Adapter** | 统一能力声明、任务状态、上下文、幂等调用、版本兼容 | 协议在 P0 就冻结，P5 只做适配实现 |

### 9.5 给 Conductor 的协议（P0 冻结）

四个基础字段（每次调用都带）：

```yaml
task_context:
  task_id: "task_001"
  project_id: "project_001"
  branch_id: "branch_001"
  correlation_id: "corr_001"
```

所有修改类调用还必须带：`idempotency_key`（Conductor 重试不重复落账）、`expected_revision`（并发修改保护）。

统一返回状态：`accepted / running / needs_author / blocked / ready / completed / failed / cancelled`，其中 `needs_author` 表示「把问题交给作者」，`blocked` 表示「依赖或权限不满足」。

### 9.6 三处硬修正

1. **guard 必须在底层写入入口**：不论模型用哪个技能、哪个插件，只要要改受保护的正文，都必须过同一套权限检查。
2. **Beat 不能成为唯一写作入口**：普通描写、环境补充、无关紧要的对话、错别字修改，不该全部经过作者授权，否则工作流会重到没人用。
3. **Conductor 不重新实现剧情判断**：Conductor 负责调度，不负责裁决；Voice 不能因为写出更好的文字就改 Beat 已确认的事实；Fade 不能因为忘了就宣告 Canon 失效；Fanfic 不能因为原著更像就推翻作者已确认的同人剧情。

### 9.7 最终判断

Beat 0.7 应成为 DSH Novel 生态里的第一个**标准化工作流插件**，而不只是一个剧情决策工具。它要证明的不只是「AI 能否听作者的话」，还有「一套插件系统能在模型不可靠时，仍然维护作者授权、剧情连续性和可追溯性」。
