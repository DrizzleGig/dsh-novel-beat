# 第 11 章实测评审结论（ChatGPT，2026-11-15）

评审对象：`docs/v0.7.0-realrun-review.md`。以下是回复要点（按原话整理，不是我的转述版本）。

## 总判断

三个问题都是真问题，但严重程度不同：**问题 2 是架构问题，问题 1 是校验时机错误，问题 3 是状态管理逻辑错误**。
不建议靠"增加更多规则、更多工具调用"修补；**不要把"段落"变成必须满足的形式指标**，
否则模型会为了通过检查而切段，而不是按创作节奏写。

| 问题 | 判断 | 优先级 |
|---|---|---|
| 1. 选中与 canon 冲突的选项后硬失败 | 必须改代码 | P0 |
| 2. 整章一次写完，节奏闸失效 | 必须改机制，不能只改提示词 | P0 |
| 3. `reset` 同名重建失败 | 必须改代码 | P1 |

## 问题 1：冲突选项可以选择，进入「可恢复的冲突解决流程」

我（代理）更正了事实：失败发生在**作者选了 B 之后**的落账校验，不是"未选中的选项连坐"。
ChatGPT 认为这比单纯时机错误更严重：**插件把 canon 冲突当成了不可恢复的提交错误，却没给作者处理冲突的机制**。
符合 Beat 定位的改法是三阶段：

1. **作者选择** — 选择先持久化（`selected_pending_resolution`）：选定方向已确定，但 canon 冲突尚未解决。
2. **处理冲突** — 分三类：普通设定冲突 → 问作者是否修改 canon；涉及其它角色/剧情的连带冲突 → 展示影响、要求确认；不可变更的硬约束 → 阻止提交但**保留原选择**。
   例：作者选「侯府投帖」，插件应问"这个选择会改变陈凡对东宫的既有态度，是否允许本次剧情改变这一设定？"
3. **正式提交** — 确认后：更新 canon、写入决策、标 `committed`、允许 `beat_compile`；这几步要事务化，不能出现"canon 已改、决策未提交"。

**最小版本**（推荐先做）：不新增决策工具、不改工具链，只增加一种可恢复的提交状态：

```
作者选择 B → 检查 canon
             ├ 无冲突 → 正常 commit
             └ 有冲突 → 保存作者选择 → 返回 conflict_pending
                        → 作者确认修改 canon → 重新校验 → 正常 commit
```

作者拒绝改 canon 时：保留选择记录，允许重新选择，**不需要重新 beat_plan**；
重复调用 `beat_next` 时不能因为存在 pending 选择就创建第二次选择或重复写账。

## 问题 2：先做最小版本 `continuation_check_required`

不加复杂状态机、不加段落字数配额：

- 只增加一个状态：**`continuation_check_required`**。
- 规则：每次 `beat_segment` 成功后设为 true；模型必须先调 `beat_plan` 判断后面还有没有真岔路；
  `beat_plan` 返回「无真实决策」→ 允许继续写；返回有效决策 → 先让作者拍板；
  **检查完成之前，拒绝下一次正文扩展写入**。

边界（要写进文档）：靠模型声明"无真实岔路"无法从代码层保证，只能靠真实写作回归评估。
另一条工程要求：**`beat_segment` 允许把整个文件登记成一个 segment，其合法性不能只靠"范围合法"**，
至少要记录当前写作单元的边界与登记时的正文版本，避免"事后整章登记冒充逐段写作"。

## 问题 3：`reset` 的执行顺序错了

现状很可能是"先查标题重复 → 发现同名 → 返回错误 → reset 根本没执行"。正确顺序：
**先判 `reset` → 清掉本章所有未拍板决策及其临时状态（保留已拍板决策与其 canon）→ 再查标题重复 → 建新决策**。

| 情况 | 处理 |
|---|---|
| 普通创建，同标题、同一章 | 拒绝 |
| `reset=true`，同标题重建 | 允许 |
| `reset=true`，有多个未拍板决策 | 全部清除 |
| 已拍板决策 | 保留 |
| 已写入 canon 的结果 | 不自动删除 |

细节：新决策分配**新 ID**，不要复用旧 ID；`reset` 要原子（失败不能留半清理状态）。

## 下一轮回归测试清单（8 条）

1. A 无冲突、B 有冲突 → 两个选项都正常展示
2. 作者选无冲突的 A → 正常拍板
3. 作者选需要改 canon 的 B → 要求确认，不直接丢弃
4. 一个 segment 登记后继续写 → 必须先完成 continuation check
5. 检查后没有真实岔路 → 允许继续写，不造假决策
6. 检查后出现真实岔路 → 必须重新让作者拍板
7. 整章一次性写入后再登记 → 不能绕过逐单元流程闸
8. `reset` 后用原来的标题 → 成功创建新决策点

其中第 7 条最重要：要验证"拒绝的是违规写入流程"，而不是"拒绝一个超过字数的 segment"。

## 最后一句

**暂时不要增加更多工具，也不要增加更多强制段落规则**。先让现有的
`beat_plan → beat_next → beat_compile → write → beat_segment` 真正形成闭环，
比起把单测从 112 个增加到 150 个，更应该看重下一次真实写作能否自然出现多个决策点。
