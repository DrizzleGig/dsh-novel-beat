# 2026-11-15 作者本人的 ChatGPT 评审（v0.7.0 方案 v3）

> 方式：ChatGPT 桌面客户端（作者账号，模型 Auto），上传 `docs/v0.7.0-chatgpt-review.md` 后按第五节 5 问作答；下方为回答原文（已去排版噪音、保留判断与依据）。
> 用途：v0.7.0 定型依据之一，与 `docs/v0.7.0-plan-v3.md`、`docs/v0.7.0-final-plan.md` 并列。

## 总判断

v3 的方向基本正确，但**目前还不应该直接发布 0.7.0**。最大问题不是工具数量、单元测试数量，而是插件**仍然没有证明自己能识别真实的剧情岔路**，而不是按照章节结构生产决策。

数据佐证：第 1 章 5 条；第 2–10 章每章恰好 3 条；第三条几乎全是章末钩子。这不是随机波动，是模板化信号——模型学会了"开局一个、中段一个、结尾一个"。

## 1. 能解决作者 5 问吗

| 作者的问题 | 当前方案 | 判断 |
| --- | --- | --- |
| 正文不可见 | 卡片回显 600 字 | 部分解决 |
| 不满意不能回退 | 级联回退 | 核心能力已解决，安全性不足 |
| 一章不能没有岔路 | 没有强制配额 | 尚未解决作者预期 |
| 决策数量固定 | 一次登记一个 | 没解决决策识别偏差 |
| 选项重复 | detail 不再拼 options | 基本解决 |

**1.1 正文可见性**：作者想看到的是生成过程，不只是登记后的记录。卡片回显保留作确认记录；完整正文仍在正常写作输出里；卡片要给"展开全文"入口；要明确区分"已写入文件"与"已登记到账本"，不能让作者觉得正文只有进了账本才算存在。

**1.2 回退**：级联逻辑正确（推翻第 1 段，后两段的依据可能全部失效），但现在的 `drift 只警告、照截断` 是危险设计——作者手工改过正文后，旧 offset 不再对应段落边界，可能截掉改过内容的一部分。建议：hash 完全匹配→自动回退；hash 不匹配但锚点唯一定位→要求作者确认；无法唯一定位→禁止自动截断，人工处理。**不能把 drift 只当提示。**

**1.3 一章没有岔路**：要区分"作者认为每章都该有值得拍板的剧情变化"和"插件是否强制每章必须登记决策"。否决强制 decisionIds 是对的（会诱导假决策），但不能因此默认作者预期不重要。建议**章节结束时做一次剧情决策审查**（本章有哪些改变故事状态的事件？哪些存在至少两种实质不同的后续？哪些已被 canon/性格/因果锁死？有没有本该交给作者却被模型自己决定的？），确实没有岔路就说明原因。注意审查本身不能变成新的第三个固定钩子。

**1.4 决策数量固定**：最严重的问题之一。"一次一问"只解决交互节奏，没解决"什么时候该问"。模型仍可以在开头/中间/结尾各问一次。要查模型是否在每章开始就隐式建了三个决策槽位——若如此，改文案没用。

**1.5 选项重复**：修复正确。还要检查作者自定义答案的显示，避免"原始选项/补充答案/结构化 changes"三处重复渲染。

## 2. 每章 3 个会不会自我维持

会，而且已经开始自我维持。模型会从工具交互学出隐式规律，形成软配额，并**为了完成预期流程反过来找能登记的事**（"先休息还是先修炼""章末留敌人还是留信件"），这些未必值得作者拍板。

推荐的密度信号（不设每章数量目标，监测独立性与重复性）：
- 决策类型：选择改变了什么 → 连续章节出现相同模板
- 决策位置：总是开局/中段/章末
- **后果差异（最看重）**：不同选项的后续剧情是否实质不同

真正的岔路应满足"选项不同 → 后续故事状态产生实质差异"（是否暴露身份、是否建立敌对关系、是否立下承诺、是否失去资源、是否改变信任关系、是否改变主线方向）；只是改描写顺序/措辞/场景安排，不该升级为剧情决策。

实现建议：决策记录加轻量字段（不强制通过）——

```json
{ "decisionRole": "relationship_change",
  "consequence": "主角与宗门长老建立敌对关系",
  "eventAnchor": "长老发现主角隐瞒修为" }
```

章节审查时做简单重复性检测，出现重复模式给**诊断**、不阻止写作。**不要把"每章恰好三个"直接变成新规则**，先观察后续 10–20 章是否自然变化。

## 3. 手工改正文后，级联回退安全吗

不安全，发布前应修。

建议**内容锚点优先、offset 辅助**（不需要 CRDT/行级 diff）：段落记录增加 `prefixHash` / `suffixHash`；回退时先比文件整体 hash → 一致直接用 offset → 不一致用内容 hash 定位 → 校验前后文上下文 → **只有唯一匹配才允许重算 offset**。作者整段重写了就是找不回来，不能模糊匹配后自动截断。

回退分三种情况：A 完全匹配→自动退；B 文件被改但原段落可唯一重定位→**要求确认**；C 无法可靠定位→**禁止自动退**。特别地：如果作者改的正是目标段本身，即使前后锚点都匹配也不能直接截断。

快照是恢复能力的一部分（不是失败后的备胎）：回退成功后写新 revision，**不删除历史 revision**，形成 revision 1→2→3→回退→revision 4 的分支。

## 4. "段 = 已定稿正文，岔路落在段尾"站得住吗

方向正确，但容易被模型误读成"每写完一段就必须登记一个决策"。

中文"段"至少三种含义（自然段 / 一段连续情节 / 一次完整写作内容），插件用的是第三种。建议保留 `segment` 技术名，提示里称**正文单元**：

- **正文单元（Segment）**：一次连续生成、已写入正文文件并完成登记的剧情内容，可含一个或多个自然段。
- **剧情岔路（Fork）**：当前故事状态允许多个有实质后果的后续走向，且尚未被设定/因果/作者决定锁定时，需要作者拍板的选择。
- **决策生效范围**：作者的决定约束后续正文单元，不追溯修改已完成的正文单元；要改已完成内容必须走重写或回退。

流程：生成正文单元 A → 写入/登记/展示 → 判断是否出现真实岔路（不是每次都有）→ 有则问、无则继续。**岔路是故事事件产生的，不是正文单元产生的。** `segment-required` 有价值，保留。

## 5. 只能先做三件事的排序

1. **`/beat fork`（最高）**：作者主动插入岔路，是对模型识别能力的补救——不能假设模型能发现所有重要岔路。支持作者给描述、给选项（也可让模型补）、拍板后进正常 `segment-required` 流程；但**不许绕过账本/状态检查/回退机制**。
2. **段落卡片「重写这一段」按钮**：功能存在 ≠ 功能可发现。按钮要显示：重写这一段、将同时作废的后续段数、将恢复的剧情状态、是否存在手工修改或 drift；点击后确认再执行级联回退，且必须继承第 3 问的安全检查。
3. **直接发布 0.7.0：暂缓**。两个未解决问题：drift 下照截断有正文损坏风险；连续九章恰好三个决策说明决策模板化。112 单测全绿只证明覆盖到的场景通过。

发布前要测**完整写作链路**：生成正文 → 登记 → 作者看到 → 模型识别岔路 → 拍板 → 继续写 → 作者手工改文件 → 尝试回退 → 验证正文完整性与账本一致性。特别覆盖：改目标段之前的正文 / 改目标段本身 / 改后续段 / 移动内容 / 删除部分正文 / 相同内容出现两次。

## 最终结论（三条核心原则）

1. **Beat 不是章节管理器，是剧情决策管理器**——不要问"每章该问几个"，要问"这里是否存在作者必须决定的不同走向"。
2. **作者的主动权必须双向**——模型发现岔路来问 + 作者发现岔路要求停下（`/beat fork`）。
3. **回退必须比生成更可靠**——宁可拒绝，也不能在无法确认目标位置时冒险截断。

优先级：**P0 修 drift 自动截断风险 → P1 `/beat fork` → P2 卡片重写按钮 → P3 决策重复模式监测 → P4 完整链路实测 → P5 发布 0.7.0**。

指标不要用"每章能提出几个决策"，改用：重要岔路被识别的比例 / 本应由作者决定却被模型擅自决定的比例 / 没必要询问的决策比例 / 作者能否随时介入 / 回退后正文与账本是否仍一致。

最后一句：v3 已有相对完整的决策执行框架，但还没证明具备可靠的剧情判断能力。不要急着加更多工具，下一阶段集中验证"该问的时候问，不该问的时候不问，作者想问的时候随时能问"。
