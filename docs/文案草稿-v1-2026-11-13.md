## 二、GitHub README 全文

````markdown
# dsh-novel-beat（拍板）

> AI 可以替你写故事，但不能替你决定故事怎么走。

你有没有遇到过这种情况：

你只想让 AI 写一章：主角参加拍卖会，拍下一块来历不明的玉佩。

结果 AI 写了三千字。

它顺手安排了一个认识玉佩的人，揭开了一段身世，安排了几个势力争夺玉佩，甚至让原本互相敌对的两个人突然站到了一起。

文字写得不错，剧情也挺热闹。

但问题是：这些发展，是你想要的吗？

你本来可能只想让玉佩成为一条慢慢展开的伏笔，而不是现在就揭开主角的身世。

更麻烦的是，写到几十章以后，AI 可能已经忘了谁知道这个秘密、谁答应过什么、哪件东西现在在谁手里。

「拍板」就是为了解决这些问题而做的。

它不替你写小说，而是在 AI 写正文之前，帮你把重要的剧情选择摆出来；写完之后，再检查这一章有没有真正落实你选定的剧情。

## 写给谁

如果你有以下创作习惯，「拍板」可能会很适合你：

- **日更或长期连载的作者**：章节越多，越容易出现前后矛盾、人物关系混乱和剧情遗忘。
- **对剧情有明确规划的作者**：不希望 AI 擅自揭露秘密、改变人物立场，或者提前消耗重要伏笔。
- **经常让 AI 辅助写正文的作者**：不想每次都重新检查 AI 有没有擅自增加重要设定。
- **正在创作复杂剧情的作者**：有多方势力、人物关系、承诺、交易、秘密和长期因果需要维护。

如果你只是让 AI 写一段日常对话，通常不需要「拍板」。它主要处理的是那些一旦发生，就会影响后续章节的剧情变化。

## 它解决什么问题

小说创作中，有些事情看起来只是一个小情节，实际上会改变整个故事。例如：

- 某个人发现了一个原本不该知道的秘密。
- 一个角色从中立转向某个阵营。
- 主角答应了别人一件尚未兑现的事情。
- 一件关键物品从一个人手里转移到了另一个人手里。
- 某个约定即将到期，人物不得不做出选择。
- 一个角色的行为改变了其他人物对他的态度。

这些事情如果交给 AI 自由发挥，很容易出现一个问题：AI 写出了一个看似合理的剧情，但这个剧情并不是作者想要的剧情。

而且，即使某一章写得没有问题，也不代表它和之前的几十章保持一致。

「拍板」把这些重要变化单独拿出来，让作者决定，再把决定留给后续章节使用。

## 它怎么工作

整个过程可以理解为三个阶段。

### 1. 写之前：先决定故事往哪里走

假设你正在写一章：林砚参加拍卖会，拍下了一块来历不明的玉佩。

正式写正文之前，「拍板」会先让 AI 把这一章里会改变走向的节点摆出来：玉佩可能暴露林砚的身世；拍卖会上的某个人可能认出了玉佩；林砚可能因此卷入两个势力之间的争夺。

它会把需要你决定的节点提出来，例如「拍卖会结束后，谁会认出这块玉佩？」，并给出几个走向：

- **没人认出。** 玉佩暂时保持神秘，身世线可以继续隐藏，但短期内缺少外部线索。
- **拍卖会的一名老者认出。** 获得一条身世线索，但林砚可能因此被人暗中关注。
- **竞争对手认出。** 玉佩立即成为双方争夺的目标，冲突提前发生，但会暴露竞争对手掌握的信息。

不同选择会带来不同的剧情后果。你可以选择其中一个，也可以根据自己的构思调整方向。最终决定权始终在作者手里。

### 2. 写的时候：按照已经决定的方向继续

当你确认了剧情走向，「拍板」会把这些决定记入这本小说共用的记录。例如：玉佩目前由林砚持有；老者已经认出玉佩；林砚尚不知道玉佩的真实来历；老者欠林砚一个解释；老者答应在下一次见面时提供线索。

下一章开始之前，这些已经确定的事情和未完成的承诺会被重新交给 AI。

这样，AI 不必每次都从零猜测故事发展到了哪里；它需要遵循已经确定的剧情事实，而不是随意创造新的版本。

### 3. 写完之后：检查这一章有没有兑现决定

正文完成后，「拍板」还会做一次结构核对。例如：

- 你已经决定老者认出了玉佩，这一章是否真的发生了这件事？
- 你已经决定玉佩仍由林砚持有，正文有没有莫名其妙地把它交给别人？
- 你已经记录了老者的承诺，这一章是否错误地写成了承诺已经兑现？

它会检查已决定的关键变化有没有发生，人物关系、秘密知情状态和物品归属有没有出现不符合记录的变化，尚未完成的承诺有没有被忽略或提前结清，正文有没有和已有剧情事实冲突的地方。

发现问题时，它会指出结构上的不一致，交给你处理。它不会因为某段剧情写得不够精彩，就判定这段正文不合格。

## 它不做什么

「拍板」管的是剧情决定和结构一致性，不接管小说创作：

- **不写正文。** 正文仍由你使用的 AI 和创作流程完成。
- **不替作者选择。** 它提供不同走向和代价，最终选择由你决定。
- **不擅自修改剧情事实。** 已经确认的记录，不会因为模型猜测而自动改变。
- **不评价文笔。** 它不判断描写是否优美、对话是否自然、情绪是否到位。
- **不保证剧情完美。** 结构核对只能发现记录范围内的矛盾和遗漏。
- **不是细纲，也不是审稿。** 细纲回答「这一章大概发生什么」，审稿回答「这一段写得好不好」；「拍板」只回答「这个节点现在选哪一个，后面还记不记得」。

它也不是一个必须一直开着的工具。默认关闭；日常对话、普通场景和过渡章节，都可以不用。

## 怎么开始

不需要改变你原来的写作习惯。

1. **安装。** 在 DeepSeek Harness 里装好插件（命令见下面「安装」），不需要再装别的小说插件。
2. **需要时开启。** 默认关闭。准备写涉及重要剧情变化的章节时，输入 `/beat on`，或点输入框旁的「拍板」按钮。
3. **先拍板，再写正文。** 让 AI 先把这一章会改变走向的节点摆出来，读完不同走向和代价，选你真正想要的那个，再继续原来的正文写作流程。写完后可以做一次结构核对。

如果这一章只是普通过渡，也可以不启用。

## 安装

```powershell
# 从 npm（推荐）
dsh plugin --profile web add dsh-novel-beat

# 或从 GitHub 源码
dsh plugin --profile web add github:DrizzleGig/dsh-novel-beat
```

装好后默认关闭。在输入框左侧点「拍板」，或输入 `/beat on` 开启；`/beat off` 关闭，`/beat status` 查看状态。开关只对当前会话生效，数据保留。

本地开发时，改完代码要「先卸再装」才会重载：

```powershell
plugin_manager set_bundle    target=dsh-novel-beat enabled=false
plugin_manager remove_bundle  target=dsh-novel-beat
plugin_manager install_bundle target=link:D:\插件\plugins\novel-beat
```

## 七个工具（给开发者和高级用户）

| 工具 | 作用 |
|---|---|
| `beat_plan` | 登记本章的决策点；每个节点 2–4 个真分叉，每个选项必须带 `changes`（entity / key / from / to / evidence），不同选项的 changes 必须不同 |
| `beat_list` | 不传 `chapter` 看全书概览；传 `chapter` 看本章；`context:true` 返回 canon + 未回收义务 + 最近决策 |
| `beat_decide` | 记录作者选择；预设选项直接快照 changes，自定义选项必须带 changes；改主意用 `supersede:true` + `reason` |
| `beat_gate` | 写正文前体检；还有未拍板就返回 `pass:false` |
| `beat_compile` | 产出本章约束（默认 `format:'self'`）：必须发生、证据、不得出现、既有义务、全书 canon |
| `beat_verify` | 写后校验：`text` 或 `path` 二选一；缺变化 / 踩禁项 / 到期义务没回应，都会给出 failure/warning |
| `beat_adjust` | 作者主权动作：`waive` 义务、`supersede` 决策；必须写 `reason` |

判定规则只有一条：**会改变故事状态的，都要问；只描述世界的，不用问。**

能往 canon 里写一条的，就是决策点——动作、知情、关系、得失、状态、承诺、时序、分叉。风、光、温度、比喻、氛围，模型自己决定。

## 数据在哪

```text
<工作区>/.dsh-novel-beat/<书名>/book.json     # 单文件账本：decisions / canon / obligations / chapters / audit
<工作区>/.dsh-novel-beat/_sessions.json       # 会话开关
<工作区>/.dsh-novel-beat/<书名>/legacy/       # 0.5 旧数据备份
```

全部在你自己电脑上的工作区里，不上传、不联网。写入是一次读-改-写，tmp → `.bak` → rename 原子落盘，按书串行化，避免并发写坏。

0.5 的 `chNNN.json` 首次访问时自动迁移：旧拍板保留为 `legacy` 决策，旧文件不删除，移到 `legacy/`。

## 边界

- `beat_verify` 是**确定性结构校验**，不是 AI 语义审稿：它查证据短语、禁项、到期义务，不判断文笔和潜台词。
- `path` 只读工作区内 `.md`/`.txt`，≤ 2 MB；`text` 直接传。
- 插件不接管正文、不写章节文件；正文由宿主模型写，由你自己保存。
- 不依赖 `novel-forge` 或任何其他插件；`format:'novel-forge'` 只是可选导出格式。

## 0.5 → 0.6 的变更

- 数据从「每章一个 `chNNN.json`」变为「每书一个 `book.json`」，自动迁移。
- `beat_plan` 的每个选项必须带 `changes`；1 个选项或只换措辞的假分叉会被拒绝。
- `beat_compile` 默认输出 `self` 契约。
- `beat_list` 的 `chapter` 变为可选。
- `novel-forge` 从工作流依赖降为可选导出格式。
````
